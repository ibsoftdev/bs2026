Esta guía te ayudará a crear el dominio WebLogic usando el Configuration Wizard con interfaz gráfica. El dominio se crea sobre la infraestructura de contenedores admin, forms y reports orquestada con Docker Compose, a partir de la imagen image_forms_14.1.2 (ver Crear imagen) y con el dominio compartido en una carpeta del host.

La guía tiene dos partes: la creación del dominio (preparación de los contenedores, schemas RCU y Configuration Wizard) y los pasos posteriores (AdminServer, OHS, Node Manager, Managed Servers y completar Reports).

0 Preparar la ejecución de contenedores con Docker Compose

El dominio WebLogic no se crea en un único contenedor “monolítico”, sino en una infraestructura de varios contenedores orquestada con Docker Compose. Todos parten de la misma imagen (image_forms_14.1.2, construida según Crear imagen) y comparten el dominio a través de una carpeta del host. Antes de crear el dominio hay que preparar ese entorno: prerrequisitos, estructura de carpetas y el archivo docker-compose.yml.

0.1. Visión general: cómo se ejecutarán los contenedores

Docker Compose define y levanta, con un solo archivo, los siguientes servicios:

Servicio (compose) Contenedor / hostname Función Cuándo se usa
admin weblogic-admin AdminServer + Node Manager. Es donde se crean los schemas RCU y el dominio (Configuration Wizard vía VNC). Desde el Paso 0 (único servicio necesario para crear el dominio).
forms weblogic-forms Managed Server WLS_FORMS con su Node Manager (FormsMachine). También se usa para compilar Forms y Pro*C. Después de crear el dominio.
reports weblogic-reports Managed Server WLS_REPORTS con su Node Manager (ReportsMachine). Después de crear el dominio.

Elementos compartidos entre los tres servicios:

  • Imagen común: image_forms_14.1.2 (con el software FMW, Forms & Reports ya instalado). Los contenedores no instalan WebLogic; solo lo ejecutan.
  • Red interna weblogic-network: permite que los contenedores se resuelvan por hostname (p. ej. forms contacta a weblogic-admin:7001).
  • Dominio en el host (./domains): el dominio vive fuera de los contenedores, por lo que sobrevive a su recreación y es el mismo para los tres.
  • Aplicaciones en el host (./app): fuentes y ejecutables (.fmb, .fmx, .pc, etc.).
  • Scripts por servicio (./scripts/<servicio>): entrypoints y utilidades (RCU, GUI, Node Manager).

Secuencia de trabajo: primero se levanta solo el servicio admin (Paso 0), se crean los schemas RCU (Paso 1) y el dominio con el Configuration Wizard (Pasos 2–4). Una vez que el dominio existe en ./domains, se levantan forms y reports (ver “Pasos Después de Crear el Dominio”).

0.3. Estructura de directorios del proyecto

Todo el trabajo con Compose se hace desde el directorio dist/, que debe tener esta estructura:

dist/
├── docker-compose.yml        ← definición de servicios, red y volúmenes
├── domains/                  ← dominio WebLogic (inicialmente vacío)
├── app/                      ← aplicaciones (forms_app/, proc_app/, ...)
└── scripts/
    ├── admin/                ← entrypoint_persistente.sh, run-rcu.sh,
    │                           install-gui-packages.sh, setup-gui.sh, ...
    ├── forms/                ← entrypoint.sh, startNodeManager.sh, create-forms-machine.py
    └── reports/              ← entrypoint.sh, startNodeManager.sh, create-reports-machine.py
cd dist
mkdir -p domains app scripts/admin scripts/forms scripts/reports
chmod +x scripts/*/*.sh

Permisos: los contenedores se ejecutan como el usuario oracle (uid 1000). Las carpetas domains/ y app/ deben ser escribibles por ese uid; de lo contrario el Configuration Wizard no podrá crear el dominio. Si es necesario:

sudo chown -R 1000:1000 domains app

0.4. Crear el archivo docker-compose.yml

El archivo docker-compose.yml describe qué contenedores se ejecutan, con qué imagen, cómo se conectan entre sí y qué carpetas del host comparten. A continuación se describen sus partes, tomando como ejemplo el servicio admin.

Partes del archivo

Clave Ejemplo (servicio admin) Papel en el proceso
services admin, forms, reports Lista de contenedores que Compose gestiona. Cada uno se puede levantar por separado (docker compose up -d admin).
image image_forms_14.1.2:r1 Imagen a partir de la cual se crea el contenedor. Debe existir localmente.
container_name / hostname weblogic-admin Nombre fijo del contenedor y hostname interno. El hostname queda registrado en la configuración del dominio (Listen Address, Machines), por lo que no debe cambiarse después de crearlo.

volumes ./domains:/u01/oracle/user_projects/domains
./app:/u01/oracle/user_projects/apps

environment ORACLE_HOME, DOMAIN_NAME, DOMAIN_HOME, ADMIN_PORT, NODE_MANAGER_PORT, PATH, LD_LIBRARY_PATH Variables que leen los scripts y las herramientas Oracle (sqlplus, rcu, WLST).

Contenido mínimo para la fase de creación del dominio

Para crear el dominio basta con el servicio admin. Crear dist/docker-compose.yml con:

services:
  # AdminServer + NodeManager
  admin:
    image: image_forms_14.1.2:r1
    container_name: weblogic-admin
    hostname: weblogic-admin
    user: oracle
    networks:
      - weblogic-network
    volumes:
      - ./domains:/u01/oracle/user_projects/domains   # dominio (persistente)
      - ./app:/u01/oracle/user_projects/apps          # aplicaciones
      - ./scripts/admin:/u01/oracle/scripts           # scripts del servicio
    environment:
      - ORACLE_HOME=/u01/oracle
      - DOMAIN_NAME=forms_domain
      - DOMAIN_HOME=/u01/oracle/user_projects/domains/forms_domain
      - ADMIN_PORT=7001
      # NO definir durante la creación del dominio (ver advertencia):
      #- ADMIN_USER=weblogic
      #- ADMIN_PASSWORD=********
      #- ADMIN_URL=t3://weblogic-admin:7001
      - NODE_MANAGER_PORT=5556
      - LD_LIBRARY_PATH=/u01/oracle/lib:/u01/oracle/oracle_common/lib
      - PATH=/u01/oracle/bin:/u01/oracle/oracle_common/bin:${PATH}
    ports:
      - "7001:7001"   # AdminServer
      - "9002:9002"   # Administration Port
      - "5556:5556"   # Node Manager
      - "7777:7777"   # OHS HTTP
      - "4443:4443"   # OHS HTTPS
      - "5902:5900"   # VNC (Configuration Wizard)
    command: ["/u01/oracle/scripts/entrypoint_persistente.sh"]
    stdin_open: true
    tty: true

networks:
  weblogic-network:
    driver: bridge

⚠️ IMPORTANTE - Variables de administración: durante la creación del dominio, ADMIN_USER, ADMIN_PASSWORD y especialmente ADMIN_URL deben estar comentadas o sin valor. Si tienen valor, pueden provocar:

  • Un boot.properties generado incorrectamente.
  • Credenciales del dominio que no coinciden con las del Wizard.
  • Errores de configuración o de autenticación al iniciar el AdminServer.

Una vez creado el dominio, se pueden habilitar si algún script las necesita.

Servicios forms y reports: no hacen falta para crear el dominio. Se agregan al mismo docker-compose.yml en la Parte 2 · Paso 5, con el YAML completo (imagen, red, volúmenes, variables del Managed Server, depends_on, healthcheck y mapeo de Node Manager 5557:5556 / 5558:5556). La referencia operativa es dist/docker-compose.yml.

0.5. Validar el archivo y levantar el contenedor admin

cd dist

# Validar sintaxis y ver la configuración resultante
docker compose config

# Crear y arrancar solo el servicio admin en segundo plano
docker compose up -d admin

# Estado y logs
docker compose ps
docker compose logs -f admin

Como el dominio todavía no existe, el log de entrypoint_persistente.sh mostrará “Contenedor en modo de configuración”. Es el estado esperado: el contenedor queda activo para ejecutar RCU y el Configuration Wizard. 

# Entrar al contenedor (como oracle o como root)
docker compose exec admin bash
docker compose exec --user root admin bash

Comandos de Compose usados en esta guía:

  • docker compose up -d <servicio>: crea/arranca un contenedor persistente.
  • docker compose exec <servicio> ...: ejecuta un comando en un contenedor que ya está corriendo.
  • docker compose run --rm <servicio> ...: crea un contenedor temporal con la misma definición y lo elimina al terminar (usado para RCU; el Wizard se ejecuta con exec en el contenedor admin).
  • docker compose down: detiene y elimina los contenedores (el dominio en ./domains se conserva).

0.6. Instalar librerías gráficas

Nota: si la imagen se construyó con la versión actual de Crear imagen, estas librerías ya vienen instaladas y este paso solo sirve como verificación (el script detecta que existen y no reinstala nada). Es necesario únicamente con imágenes anteriores.

Para ejecutar el Configuration Wizard con interfaz gráfica, instala las librerías gráficas en el contenedor admin que está corriendo:

docker compose exec --user root admin /u01/oracle/scripts/install-gui-packages.sh

Este script instala los siguientes paquetes:

Paquete Función
xorg-x11-server-Xvfb Xvfb (X Virtual Framebuffer): display virtual para ejecutar aplicaciones gráficas sin pantalla física.
xorg-x11-twm, xorg-x11-xinit twm (Tab Window Manager): gestor de ventanas básico, y utilidades de arranque de X.
x11vnc Servidor VNC para ver el display virtual desde el host (si no está en los repositorios base, el script lo instala desde EPEL).
xorg-x11-utils, xorg-x11-server-utils Utilidades X11; incluyen xauth y xhost, necesarias para que Java se conecte al display.
dbus-x11 Sistema de mensajería que requieren algunas aplicaciones gráficas Java.

¿Por qué como root y cuándo repetirlo?

  • Instalar paquetes con yum requiere privilegios de administrador; por eso se usa --user root. El contenedor sigue ejecutando WebLogic como oracle.
  • Lo que se instala con docker compose exec queda en el contenedor, no en la imagen. Se mantiene mientras el contenedor admin exista, pero hay que repetir este paso cada vez que se recrea (p. ej. tras docker compose down o docker compose up --force-recreate).
  • No usar docker compose run --rm para esta instalación: crea un contenedor temporal que se elimina al terminar, y los paquetes se pierden.

✓ Verificación: al finalizar, el script comprueba que los comandos (Xvfb, twm, x11vnc, xhost) estén disponibles y muestra "✓ Instalación de paquetes GUI completada". Si muestra "Instalación completada con advertencias", revisar los logs en /tmp/yum-*.log dentro del contenedor.

Nota: Si el script install-gui-packages.sh no está disponible, puedes instalar los paquetes manualmente:

docker compose exec --user root admin yum install -y xorg-x11-server-Xvfb xorg-x11-twm xorg-x11-xinit x11vnc xorg-x11-utils xorg-x11-server-utils dbus-x11

1 Crear los Schemas RCU (Repository Creation Utility)

⚠️ IMPORTANTE: Los schemas RCU deben crearse ANTES de ejecutar el Configuration Wizard. El dominio WebLogic requiere estos schemas para funcionar correctamente con JRF (Java Required Files).

Los schemas se crean con RCU en modo silencioso, desde el contenedor admin que quedó corriendo en el Paso 0.5. No requiere entorno gráfico.

1.1. Ejecutar RCU

Abrir una shell en el contenedor:

cd dist
docker compose exec admin bash

Dentro del contenedor, ejecutar:

/u01/oracle/oracle_common/bin/rcu -silent -createRepository \
  -connectString 192.168.1.109:33118:ORA193PDB1 \
  -dbUser sys -dbRole sysdba \
  -schemaPrefix DIST \
  -component MDS \
  -component OPSS \
  -component IAU \
  -component IAU_APPEND \
  -component IAU_VIEWER \
  -component STB \
  -component WLS
ParámetroDescripción
-connectStringServidor de base de datos en formato host:puerto:servicio. Ajustar al entorno.
-dbUser sys -dbRole sysdbaUsuario con privilegios para crear usuarios y tablespaces
-schemaPrefix DISTPrefijo de los schemas, sin guion bajo. RCU lo agrega automáticamente: DIST_<COMPONENTE>. No escribas DIST_ como prefijo.
-component ...Componentes que requieren JRF, Forms y Reports. WLS es obligatorio: crea DIST_WLS y DIST_WLS_RUNTIME, que el Wizard pide en la Pantalla 7.

1.2. Responder las contraseñas

RCU solicita las contraseñas de forma interactiva:

  1. Primero, la contraseña del usuario sys de la base de datos.
  2. Luego, una contraseña por cada schema que va a crear.

⚠️ Usa la misma contraseña para todos los schemas, por ejemplo oracle01. En la Pantalla 6 del Configuration Wizard se ingresa una única contraseña que se aplica a todos los datasources. Si algún schema tiene una clave distinta, la prueba de la Pantalla 8 (JDBC Test) fallará para ese schema.

Tip: para no responder la contraseña schema por schema, agrega esta opción al comando. RCU pedirá solo dos claves: la de sys y una común para todos los schemas.

  -useSamePasswordForAllSchemaUsers true

1.5. Borrar los schemas RCU (si hay que recrearlos)

Opción A: con RCU. Dentro del contenedor admin, usa el mismo comando de creación con -dropRepository e incluye todos los componentes:

/u01/oracle/oracle_common/bin/rcu -silent -dropRepository \
  -connectString 192.168.1.109:33118:ORA193PDB1 \
  -dbUser sys -dbRole sysdba \
  -schemaPrefix DIST \
  -component MDS -component OPSS -component IAU \
  -component IAU_APPEND -component IAU_VIEWER \
  -component STB -component WLS

Si algún schema ya no existe, RCU muestra Failed para ese componente. Es esperado.

Opción B: manualmente con SQL (si RCU falla o deja residuos). -dropRepository puede dejar usuarios huérfanos, por ejemplo si se omitió WLS, o el prefijo registrado en la metadata de RCU. En ese caso, al recrear los schemas RCU responde que el prefijo DIST ya está en uso.

Conectarse a la base de datos desde el contenedor (SQL*Plus pedirá la contraseña de sys):

cd dist
docker compose exec admin sqlplus sys@//192.168.1.109:33118/ORA193PDB1 as sysdba

Dentro de SQL*Plus:

-- Borrar los schemas
DROP USER DIST_OPSS CASCADE;
DROP USER DIST_IAU_APPEND CASCADE;
DROP USER DIST_IAU_VIEWER CASCADE;
DROP USER DIST_IAU CASCADE;
DROP USER DIST_MDS CASCADE;
DROP USER DIST_STB CASCADE;
DROP USER DIST_WLS_RUNTIME CASCADE;
DROP USER DIST_WLS CASCADE;

-- Limpiar la metadata de RCU
DELETE FROM SYSTEM.SCHEMA_VERSION_REGISTRY WHERE MRC_NAME = 'DIST';
COMMIT;

-- Verificar: ambas consultas no deben devolver filas
SELECT username FROM dba_users WHERE username LIKE 'DIST\_%' ESCAPE '\';
SELECT mrc_name, comp_id FROM SYSTEM.SCHEMA_VERSION_REGISTRY WHERE MRC_NAME = 'DIST';
EXIT;

Si un DROP USER responde ORA-01918: user does not exist, ese schema ya estaba borrado y se puede continuar.

⚠️ Precaución: estas sentencias borran los schemas y sus datos de forma irreversible. Confirma que el prefijo es DIST y que ningún otro dominio usa esos schemas. Después del borrado, el dominio existente deja de funcionar hasta que se recreen los schemas y el dominio.

Sobre scripts/admin/run-rcu.sh: el dominio no se creó con este script. En su versión actual no incluye el componente WLS, así que no crea DIST_WLS ni DIST_WLS_RUNTIME y el Wizard fallaría en la Pantalla 7. No lo uses hasta corregirlo.

2 Ejecutar el Configuration Wizard

El Configuration Wizard se ejecuta dentro del contenedor admin que quedó corriendo en el Paso 0.5, usando el entorno gráfico (display :99 y VNC) preparado en el Paso 0.7. No se crea ningún contenedor adicional.

Verificación Comando / referencia

Los schemas RCU existen (Paso 1) docker compose exec admin /u01/oracle/scripts/check-rcu-schemas.sh

2.2. Iniciar el Wizard

cd dist
docker compose exec admin /u01/oracle/scripts/run-config-wizard.sh

El script run-config-wizard.sh:

  1. Comprueba que Xvfb esté instalado; si no está corriendo en el display :99, ejecuta setup-gui.sh para iniciarlo.
  2. Define DISPLAY=:99 y XAUTHORITY.
  3. Comprueba x11vnc y lo inicia en el puerto 5900 si no está corriendo (publicado en el host como 5902).
  4. Ejecuta el Configuration Wizard: $ORACLE_HOME/oracle_common/common/bin/config.sh.

La terminal queda ocupada mientras el Wizard está abierto; al cerrarlo, el comando termina. El Wizard se maneja desde VNC Viewer (Paso 3).

⚠️ Ejecutar como oracle, no como root: el comando anterior no usa --user root a propósito. El servicio admin corre como oracle y el dominio debe crearse con ese propietario; si se crea como root, el AdminServer y los Managed Servers tendrán problemas de permisos al iniciar. --user root solo se usa para instalar paquetes (Paso 0.6) o iniciar el entorno gráfico (Paso 0.7).

No usar docker compose run para el Wizard. Un contenedor temporal con -p 5902:5900 falla porque el puerto 5902 ya lo publica el contenedor admin, y además no tendría el entorno gráfico preparado en el Paso 0.7.

Si el script indica que falta Xvfb o x11vnc (imágenes anteriores a la que incluye las librerías gráficas), volver a los Pasos 0.6 y 0.7 y repetir este paso.

Pantalla 12: Managed Servers (Servidores Gestionados)

Esta pantalla muestra los Managed Servers que se crearán automáticamente para Forms y Reports.

¿Qué es un Managed Server?

Un dominio WebLogic tiene dos tipos de servidores, cada uno con su propia JVM:

  • AdminServer (Pantalla 10): administra el dominio. Aloja la consola (/console), Enterprise Manager (/em) y la configuración central. No ejecuta las aplicaciones de negocio.
  • Managed Servers: ejecutan las aplicaciones. Reciben su configuración del AdminServer al arrancar y se pueden iniciar, detener y reiniciar de forma independiente, normalmente a través del Node Manager.

Al seleccionar las plantillas de Forms y Reports en la Pantalla 2, el Wizard crea un Managed Server para cada producto. En esta arquitectura cada uno corre en su propio contenedor:

Managed ServerContenedorAplicación desplegadaURL de accesoServer Group
WLS_FORMSweblogic-formsformsapphttp://<host>:9001/forms/frmservletFORMS-MAN-SVR
WLS_REPORTSweblogic-reportsreportshttp://<host>:9012/reports/rwservletREPORTS-APP-SERVERS

WLS_FORMS (Oracle Forms Services):

  • Aloja la aplicación formsapp, que contiene el Forms Listener Servlet (/forms/frmservlet). Es el punto de entrada de los usuarios, que se conectan mediante Java Web Start o FSAL (Forms Standalone Launcher).
  • Por cada sesión de usuario, el servlet lanza un proceso nativo frmweb (Forms Runtime) que ejecuta los módulos compilados .fmx, .mmx y .plx y se conecta a la base de datos de la aplicación.
  • Como frmweb es un binario nativo, este servidor depende de las librerías compartidas generadas con genshlib y de libaio, que ya incluye la imagen (ver Crear imagen).
  • Su configuración está en formsweb.cfg (parámetros de cada aplicación Forms) y en default.env (variables de entorno del runtime, como FORMS_PATH y TNS_ADMIN).

WLS_REPORTS (Oracle Reports Services):

  • Aloja la aplicación reports, que expone el servlet /reports/rwservlet para solicitar la ejecución de reportes.
  • Incluye el Reports Server in-process: ejecuta los reportes .rdf y .rep, gestiona la cola de trabajos y genera la salida (PDF, HTML, etc.).
  • Las aplicaciones Forms lo invocan con RUN_REPORT_OBJECT o WEB.SHOW_DOCUMENT apuntando a rwservlet. También puede llamarse directamente por URL.

Server Groups: el valor FORM... o REPO... que se ve truncado en la columna "Server Groups" corresponde a FORMS-MAN-SVR y REPORTS-APP-SERVERS. Esos grupos le indican al Wizard qué aplicaciones, librerías y servicios desplegar en cada servidor. No los cambies: si un Managed Server queda sin su grupo, no tendrá desplegado formsapp o reports.

Si solo necesitas uno de los dos productos, igual conviene mantener ambos servidores. Un servidor que no se arranca no consume recursos, y agregarlo después requiere reconfigurar el dominio.

7.3. Preparar $DOMAIN_HOME/reports (directorios y lanzadores)

Las plantillas de los lanzadores están en $ORACLE_HOME/bin (rwengine.sh, reports.sh, rwrun.sh, rwserver.sh…). Contienen marcadores que normalmente sustituye el instalador: $$domain_home$$, $$mw_home$$, $$component_name$$ y %HOME%. Sin sustituir no funcionan, porque $$ se expande al PID del shell.

El script prepare-reports-domain.sh hace todo el paso de forma idempotente:

  • crea reports/{bin,server,cache,temp,fonts};
  • copia los lanzadores desde $ORACLE_HOME/bin;
  • sustituye los marcadores con el DOMAIN_HOME, el ORACLE_HOME y la instancia de Reports Tools;
  • verifica que no quede ningún marcador.
# Diagnóstico (no modifica nada)
docker compose exec -u oracle reports /u01/oracle/scripts/prepare-reports-domain.sh --check

# Aplicar (incluye 7.4 para DEV)
docker compose exec -u oracle reports /u01/oracle/scripts/prepare-reports-domain.sh \
  --source-dir /u01/oracle/user_projects/apps/reports_app/src \
  --disable-security

Equivalente manual:

export DOMAIN_HOME=/u01/oracle/user_projects/domains/forms_domain
mkdir -p $DOMAIN_HOME/reports/{bin,server,cache,temp,fonts}
cp -p /u01/oracle/bin/reports.sh /u01/oracle/bin/rw*.sh $DOMAIN_HOME/reports/bin/
chmod 750 $DOMAIN_HOME/reports/bin/*.sh
cd $DOMAIN_HOME/reports/bin
sed -i \
  -e 's#\$\$domain_home\$\$#/u01/oracle/user_projects/domains/forms_domain#g' \
  -e 's#\$\$mw_home\$\$#/u01/oracle#g' \
  -e 's#\$\$component_name\$\$#reptools1#g' \
  -e 's#%HOME%#/home/oracle#g' \
  *.sh
grep -n '\$\$\|%[A-Z_]*%' *.sh      # debe quedar vacío

7.4. Ajustar rwserver.conf: sourceDir y seguridad (DEV)

Archivo: $DOMAIN_HOME/config/fmwconfig/servers/WLS_REPORTS/applications/reports_14.1.2/configuration/rwserver.conf

  • sourceDir: descomentar la propiedad del motor rwEng y apuntarla a la carpeta de los .rdf: 
    <engine id="rwEng" class="oracle.reports.engine.EngineImpl" maxEngine="1" minEngine="1" engLife="50" >
   <property name="sourceDir" value="/u01/oracle/user_projects/apps/reports_app/src"/>
  • Seguridad: por defecto el job de reportes lleva securityId="rwJaznSec", y cada petición pide un usuario de WebLogic con rol de Reports. Para DEV, o para llamadas desde Forms sin authid, se elimina ese atributo: 
    <job jobType="report" engineId="rwEng"/>
    Si se mantiene la seguridad, hay que otorgar roles con WLST: 
    grantAppRole(appStripe="reports", appRoleName="RW_ADMINISTRATOR",
             principalClass="weblogic.security.principal.WLSUserImpl", principalName="weblogic")

El aviso SecurityHelper:start Writeable folders not configured solo afecta a destype=file (requiere folderAccess en rwserver.conf). No impide destype=cache.
