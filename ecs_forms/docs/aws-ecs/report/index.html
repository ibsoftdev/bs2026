reports-server sobre el cluster forms_report, alineado con Forms

Visión general

Guía paso a paso para crear la task definition reports-server y su servicio en el cluster forms_report, registrado en Cloud Map como weblogic-reports.forms.local, arrancar el managed server WLS_REPORTS, completar Reports en el dominio y validarlo con un reporte real. Parte de lo creado en la guía del Contenedor AdminServer (infraestructura, cluster, red y hostnames) y sigue el esquema del Contenedor Forms; lo compartido se referencia en lugar de repetirse.

1 Crear task definition ReportsHecho

La task definition reports-server describe el contenedor del managed server WLS_REPORTS. Sigue el mismo asistente que la del AdminServer (Admin 3, donde se explica cada sección). Cambian el nombre, los puertos, las variables, la carpeta de scripts y el log group.

ECS → Definiciones de tareas → Crear nueva definición de tarea. No partir de Crear nueva revisión sobre forms-server: cambiaría la familia de Forms. Para partir de su configuración usar el JSON del anexo con Crear nueva definición de tarea con JSON.

1.4 · Comando y directorio de trabajo

Punto de entrada sh,-c, comando sleep infinity, directorio /u01/oracle: la tarea queda viva para entrar por ECS Exec y arrancar WLS_REPORTS a mano (por qué, en Admin 3.5). Cuando el arranque sea estable se puede cambiar por un script de arranque en una nueva revisión, como en Admin 7d.

1.7 · Crear el log group /ecs/reports-server (obligatorio)

Aunque la TD lleva awslogs-create-group=true, ecsTaskExecutionRole no tiene permiso logs:CreateLogGroup. Si el grupo no existe, la tarea queda Detenida con ResourceInitializationError: failed to validate logger args ... AccessDeniedException ... logs:CreateLogGroup. /ecs/forms-admin y /ecs/forms-server ya existían, por eso no ocurrió con admin ni Forms.

  1. CloudWatch → Registros → Administración de registros → Crear un grupo de registros.
  2. Nombre /ecs/reports-server (con la barra inicial); retención No vence nunca; clase Estándar; sin KMS.
  3. Crear.
aws logs create-log-group --log-group-name /ecs/reports-server --region us-east-1

Si el servicio ya existía y sus tareas fallaron por esto: Actualizar servicio → Forzar nueva implementación.

2 Crear servicio + Service DiscoveryHecho

El servicio reports-server mantiene una tarea Reports en ejecución. El asistente es el mismo que el del servicio admin (Admin 4, con cada sección explicada); cambian el nombre de Service Discovery y la apertura del puerto 9012.

2.1 · Crear el servicio

  1. Cluster forms_report → pestaña Servicios → Crear.
  2. Familia reports-server (revisión más reciente); nombre reports-server; tareas deseadas 1.
  3. Cómputo Fargate, plataforma LATEST, ECS Exec encendido.

2.2 · Opciones de implementación

Actualización acumulativa, mín. 0 % / máx. 200 % (Admin 4.3). El mínimo 0 % evita que durante un redespliegue convivan dos WLS_REPORTS escribiendo sobre el mismo dominio en EFS.

2.3 · Service Discovery weblogic-reports

Registra la tarea como weblogic-reports.forms.local, el host que usan ReportsMachine, el Node Manager de Reports y Coherence. Mismo procedimiento que weblogic-admin (Admin 4.6).

CampoValor
Espacio de nombresExistente: forms.local (ns-r3zqawwpjtp5pzue)
Servicio de detecciónNuevo: weblogic-reports
Registro DNS / TTLA / 15 · propagación de estado ECS habilitada
Completar esta sección antes de pulsar Crear: solo se puede asociar al crear el servicio.

2.4 · Redes del servicio

Misma red que admin: solo pub-A, SG forms-sg-ecs e IP pública activada (Admin 4.9). La ruta a la BD ya existe en Pub-RT (Admin 4.10); no asociar database-A.

2.5 · Regla de entrada 9012 en forms-sg-ecs

Para acceder a rwservlet desde fuera se abre el 9012 en el security group compartido (Admin 1.2), desde EC2 → Grupos de seguridad, no desde el asistente. La regla interna Todo el tráfico cubre Node Manager, Administration Port y Coherence entre los tres contenedores.

PuertoUsoOrigen recomendado
9012Reports HTTP (rwservlet)IP de administración /32 o red corporativa
9512Reports HTTPSNo se abre en DEV
9992 · 5556 · UDP 7574Administration Port · Node Manager · CoherenceSolo regla interna del SG
Coherence (defaultCoherenceCluster, compartido por cluster_forms y cluster_reports) descubre miembros por UDP 7574. Si la regla interna es solo Todos los TCP, agregar Todos los UDP con el mismo origen. 0.0.0.0/0 en 9012 solo en DEV.

2.6 · Crear

La consola vuelve al cluster con el aviso “La implementación de reports-server está en curso”.

3 Verificar Running, Cloud Map y ECS ExecHecho

Como en admin (Admin 5): esperar la tarea en Ejecutando (la descarga de la imagen tarda ~5 min), comprobar el registro weblogic-reports en Cloud Map y entrar con ECS Exec: 

aws ecs execute-command \
  --cluster forms_report \
  --task <TASK_ID> \
  --container reports-server \
  --interactive \
  --command "su -s /bin/bash oracle"
df -h | grep -E 'domains|apps|scripts'
ls /u01/oracle/scripts          # scripts de reports

# DNS Cloud Map: debe coincidir con la IP VPC de la tarea (eth1), no con 169.254.x.x
getent hosts weblogic-reports.forms.local weblogic-admin.forms.local weblogic-forms.forms.local
ip -4 -o addr show | awk '{print $2,$4}'

timeout 5 bash -c 'echo >/dev/tcp/weblogic-admin.forms.local/7001' && echo OK || echo FAIL   # AdminServer
timeout 5 bash -c 'echo >/dev/tcp/192.168.229.137/1521' && echo OK || echo FAIL              # BD Oracle

4 Verificar hostnames del dominioHecho

ReportsMachine y nodemanager_reports/nodemanager.properties deben usar weblogic-reports.forms.local. El ajuste lo hace set-cloudmap-hostnames.sh una sola vez para las tres Machines (Admin 6); aquí solo se verifica: 

grep -n 'weblogic-reports' $DOMAIN_HOME/config/config.xml $DOMAIN_HOME/nodemanager_reports/nodemanager.properties
# Esperado: solo weblogic-reports.forms.local, nunca el nombre corto
Con el nombre corto, el Node Manager falla con UnknownHostException y WLS_REPORTS queda fuera del WKA de Coherence (Hostname weblogic-reports ... failed to resolve): a los 300 s pasa a FAILED. Si falta, aplicar Admin 6 con todos los servidores detenidos.

5 Arrancar Node Manager y WLS_REPORTSHecho

Con el AdminServer en RUNNING (Admin 7), se arranca el Node Manager de ReportsMachine (lo necesitan el AdminServer y la creación de Reports Tools del Paso 6) y luego WLS_REPORTS, desde la sesión ECS Exec del Paso 3.

5.1 · Credenciales de arranque (boot.properties)

mkdir -p "$DOMAIN_HOME/servers/WLS_REPORTS/security"
cat > "$DOMAIN_HOME/servers/WLS_REPORTS/security/boot.properties" <<EOF
username=weblogic
password=<clave>
EOF
chmod 600 "$DOMAIN_HOME/servers/WLS_REPORTS/security/boot.properties"
WebLogic cifra el archivo en el primer arranque. export WLS_USER / WLS_PW no sirve: startManagedWebLogic.sh las reinicia vacías. No confundir con el boot.properties de Node Manager (.../data/nodemanager/).

5.2 · Node Manager de ReportsMachine

nohup /u01/oracle/scripts/startNodeManager.sh \
  > "$DOMAIN_HOME/nodemanager_reports/nm_console.out" 2>&1 &

tail -f "$DOMAIN_HOME/nodemanager_reports/nodemanager.log"
# Esperado: "Secure socket listener started on port 5556, host weblogic-reports.forms.local"

5.3 · Arrancar WLS_REPORTS

Opción recomendada — startWLSReports.sh (como root u oracle): valida boot.properties y el AdminServer, limpia .lok, arranca en segundo plano y espera RUNNING + HTTP 200 de /reports/rwservlet: 

/u01/oracle/scripts/startWLSReports.sh
# Reinicio:
pkill -f 'weblogic.Name=WLS_REPORTS'; sleep 10; /u01/oracle/scripts/startWLSReports.sh

Para monitorear el inicio:

tail -100f /u01/oracle/user_projects/domains/forms_domain/servers/WLS_REPORTS/logs/WLS_REPORTS.log
# Esperado: <Server state changed to RUNNING.>

Alternativas: WebLogic Remote Console (Servidores → WLS_REPORTS → Iniciar), WLST (connect(...); start('WLS_REPORTS','Server')) o ./bin/startManagedWebLogic.sh WLS_REPORTS t3://weblogic-admin.forms.local:7001 en segundo plano.

5.4 · Targets de la aplicación reports

Remote Console (o WLST) → Deployments → reports#14.1.2 → Targets: desmarcar AdminServer y marcar WLS_REPORTS (o cluster_reports), si no se hizo al crear el dominio. Si sigue en AdminServer, /reports/rwservlet no responde en 9012.

5.5 · Arranque automático de WLS_REPORTS al iniciar la tareaHecho

Validado el arranque manual (5.3), se cambia el comando del contenedor para que la tarea inicie WLS_REPORTS sin intervención, igual que el AdminServer (Admin 7d) y WLS_FORMS (Forms 5d): nueva revisión de la task definition y actualización del servicio.

  1. ECS → Definiciones de tareas → reports-server → última revisión → Crear nueva revisión.
  2. Contenedor reports-server → Configuración de Docker:
    • Punto de entrada: vacío.
    • Comando: /u01/oracle/scripts/startWLSReports.sh,-keep (reemplaza a sleep,infinity).
    • Directorio de trabajo: /u01/oracle (sin cambios).
  3. Crear → nueva revisión (reports-server:N).
  4. Cluster forms_report → servicio reports-server → Actualizar → revisión reports-server:N → Forzar nueva implementación → Actualizar.
  5. Con la nueva tarea en Ejecutando, validar RUNNING con el tail de WLS_REPORTS.log (5.3) y el reporte de prueba (Paso 7).

Equivalente en el JSON de la task definition:

"command": ["/u01/oracle/scripts/startWLSReports.sh", "-keep"]

Con -keep, si el AdminServer aún no responde (tareas lanzadas a la vez), el script lo espera hasta WAIT_TIMEOUT (600 s) antes de arrancar WLS_REPORTS; la tarea sigue viva aunque el managed server falle, para poder entrar por ECS Exec a revisar. Sin -keep la tarea termina al fallar o al alcanzar RUNNING, por lo que no sirve como comando del contenedor.

El script se ejecuta desde el EFS (/u01/oracle/scripts): debe existir con permiso de ejecución (chmod +x startWLSReports.sh) y requiere el boot.properties de 5.1. El Node Manager de ReportsMachine no se arranca automáticamente: si hace falta (consola, Reports Tools del Paso 6), iniciarlo por ECS Exec como en 5.2.

El Configuration Wizard no crea la instancia de Reports Tools ni $DOMAIN_HOME/reports. WLS_REPORTS llega a RUNNING y /reports/rwservlet responde 200, pero el primer reporte falla con REP-52266 / REP-51002. Se hace una sola vez: queda en el EFS y sobrevive a los redespliegues. Detalle en la guía de creación del dominio, Paso 7: Completar Reports.

6.1 · Instancia de Reports Tools

Con el Node Manager de ReportsMachine arriba (5.2), en reports-server como oracle:

Al consultar getserverinfo con credenciales válidas, la respuesta por defecto es REP-52262: Diagnostic output is disabled. No es una falla: WLS_REPORTS y rwservlet responden y la autenticación pasó; solo indica que los comandos de diagnóstico del servlet están deshabilitados (valor por defecto de Oracle, recomendado en producción porque exponen la configuración del server).

Para habilitarlo temporalmente (solo en desarrollo), en el rwservlet.properties de WLS_REPORTS cambiar <diagnostic>no</diagnostic> por <diagnostic>yes</diagnostic> y reiniciar WLS_REPORTS (5.3): 
find $DOMAIN_HOME/config/fmwconfig/servers/WLS_REPORTS -name rwservlet.properties
grep -n diagnostic <ruta>/rwservlet.properties
Volver a no al terminar las pruebas.

Anexo Imagen r2: construir, subir a ECR y actualizar serviciosHecho

r2 = r1 + motif libX11 libXext libXt libXp, necesarias para librw.so / librwu.so del motor de Reports. Las imágenes construidas con el Dockerfile.wls actual ya las incluyen (Crear imagen, puntos 4.e y 7.a). El repositorio ECR y el envío se explican en Admin 1.1.

1 · Construir r2 a partir de r1 (local)

cd dist/html/docker/crear_imagen
docker build -f Dockerfile.r2 \
  --build-arg BASE_IMAGE=image_forms_14.1.2:r1 \
  --build-arg RUN_USER=$(docker inspect -f '{{.Config.User}}' image_forms_14.1.2:r1) \
  -t image_forms_14.1.2:r2 .

2 · Subir a ECR

aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin 730335573515.dkr.ecr.us-east-1.amazonaws.com
docker tag image_forms_14.1.2:r2 730335573515.dkr.ecr.us-east-1.amazonaws.com/forms-docker:r2
docker push 730335573515.dkr.ecr.us-east-1.amazonaws.com/forms-docker:r2

3 · Nueva revisión de TD + forzar despliegue (los tres servicios)

TD → última revisión → Crear nueva revisión → URI de imagen …/forms-docker:r2 → Crear. Luego en el servicio: Actualizar → nueva revisión → Forzar nueva implementación (mismo procedimiento que Admin 7d). Repetir en admin, forms y reports-server.

Con sleep infinity, cada redespliegue reinicia el contenedor sin WebLogic: hay que volver a arrancar AdminServer, Node Manager y los managed (Paso 5). El dominio, reports/ y los scripts persisten en EFS, así que el Paso 6 no se repite.

Anexo Comandos AWS CLIHecho

Los comandos de infraestructura compartida (subnets, rutas, security groups, EFS, Session Manager Plugin, redespliegue) están en el anexo CLI de admin. Aquí los específicos de reports-server, incluida su creación completa por CLI.

1 · Registrar la task definition

aws ecs register-task-definition --cli-input-json file://conf_json/reports-server.json --region us-east-1

2 · Servicio Cloud Map weblogic-reports

Solo si el servicio ECS se crea por CLI (desde la consola se crea en el Paso 2.3).

aws servicediscovery create-service \
  --name weblogic-reports \
  --namespace-id ns-r3zqawwpjtp5pzue \
  --dns-config 'NamespaceId=ns-r3zqawwpjtp5pzue,RoutingPolicy=MULTIVALUE,DnsRecords=[{Type=A,TTL=15}]' \
  --health-check-custom-config FailureThreshold=1 \
  --region us-east-1 --query 'Service.Arn' --output text

3 · Crear el servicio ECS

aws ecs create-service \
  --cluster forms_report \
  --service-name reports-server \
  --task-definition reports-server \
  --desired-count 1 \
  --launch-type FARGATE \
  --platform-version LATEST \
  --enable-execute-command \
  --deployment-configuration 'minimumHealthyPercent=0,maximumPercent=200' \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-01212efd4a9ce759b],securityGroups=[sg-0e1787d32bac71fcd],assignPublicIp=ENABLED}' \
  --service-registries 'registryArn=<ARN_SERVICIO_CLOUDMAP_WEBLOGIC_REPORTS>' \
  --region us-east-1

4 · Abrir 9012 en el SG (desde una IP concreta)

aws ec2 authorize-security-group-ingress --group-id sg-0e1787d32bac71fcd \
  --protocol tcp --port 9012 --cidr <MI_IP>/32 --region us-east-1

5 · Tarea, IP pública y logs

TASK_ARN=$(aws ecs list-tasks --cluster forms_report --service-name reports-server \

★ Lecciones críticas

Las lecciones de infraestructura comunes (rol de tarea, timeout de ECR, espacio efímero, NFS 2049, rutas EFS, sleep infinity y PATH, Service Discovery al crear, solo pub-A + ruta BD, hostnames) están en las lecciones de admin, y las de WebLogic en contenedor (usuario oracle, boot.properties, zombies, ECS Running ≠ WebLogic RUNNING, libaio en la imagen, URL de BD fija en el dominio) en las lecciones de Forms. Propias de Reports:

  1. Log group creado a mano (Paso 1.7) — ecsTaskExecutionRole no tiene logs:CreateLogGroup; awslogs-create-group=true no basta.
  2. Librerías X11/Motif en la imagen (anexo r2) — sin libXm.so.4, libX11, libXext, libXt, libXp, la primera petición a rwservlet queda colgada con DFW-99998 UnsatisfiedLinkError.
  3. Coherence por UDP 7574 (Paso 2.5) — la regla interna del SG debe incluir UDP; si no, WLS_REPORTS queda en Delaying formation of a new cluster y a los 300 s pasa a FAILED.
  4. FQDN de ReportsMachine (Paso 4) — el nombre corto deja a WLS_REPORTS fuera del WKA de Coherence.
  5. Puertos propios (Paso 1.2) — 9012/9512/9992; el mapeo 5558:5556 de compose no aplica en Fargate.
  6. Carpeta scripts/reports en EFS (Paso 0) — debe existir antes de lanzar la tarea, o falla el montaje.
  7. Node Manager separado (Paso 5.2) — nodemanager_reports, con ListenAddress=weblogic-reports.forms.local.
  8. Memoria (Paso 1.1) — los engines rwEng consumen memoria aparte de la JVM; 8 GB si hay OutOfMemory / exit 137.
  9. Target de reports#14.1.2 (Paso 5.4) — si sigue en AdminServer, rwservlet no responde en 9012.
  10. El Wizard no completa Reports (Paso 6) — faltan Reports Tools y $DOMAIN_HOME/reports/{bin,server,cache,temp,fonts}; la causa real solo aparece en rwserver_diagnostic.log.
  11. createReportsToolsInstance necesita el Node Manager de ReportsMachine (Paso 6.1) — sin él, la instancia queda sin archivos.
  12. Lanzadores con marcadores (Paso 6.2) — rwengine.sh y reports.sh traen $$domain_home$$, $$mw_home$$, $$component_name$$ y %HOME%; copiarlos sin sustituir no funciona.
  13. Seguridad de Reports activa por defecto — securityId="rwJaznSec" pide usuario en cada reporte; en DEV se elimina.
  14. TNS y sourceDir en EFS (Pasos 6–7) — para que sobrevivan a un redespliegue.
  15. RDF en modo carácter (Paso 7) — REP-1920 con desformat=PDF; usar mode=bitmap.
