Visión general

Guía paso a paso para preparar la infraestructura en AWS (imagen en ECR, cluster forms_report, EFS rector-dev, security groups y rol de tarea) y crear la task definition forms-admin y su servicio, registrado en Cloud Map como weblogic-admin.forms.local.

1 Configuraciones comunes del ClusterHecho

Antes de crear el cluster y la task definition, dejar listas las piezas compartidas por los tres contenedores (admin, forms y reports): la imagen en ECR, el security group de las tareas, el EFS del dominio, el rol de tarea para ECS Exec y el namespace Cloud Map forms.local.

1.1 · Imagen en ECRHecho

Subir a ECR la imagen construida en la fase Crear la imagen. Los tres servicios (admin, forms, reports) usan la misma imagen.

1.1a · Crear el repositorio privado

Amazon ECR (Elastic Container Registry) es el registro de imágenes Docker de AWS. ECS Fargate no puede usar la imagen que está en la máquina local: la descarga de un repositorio ECR al lanzar cada tarea. Este repositorio privado guarda la imagen Oracle Forms/Reports 14.1.2 y solo es accesible con credenciales de la cuenta.

Amazon ECR → Registro privado → Repositorios → Crear repositorio.

1.1c · Subir la imagen

Se publica en el repositorio la imagen construida localmente: primero se autentica Docker contra ECR, luego se etiqueta la imagen con la URI del repositorio y por último se envía (push). Por el tamaño de la imagen (~11 GB) el envío tarda varios minutos y conviene hacerlo desde una máquina con buena conexión.

El botón Ver comandos de envío del repositorio muestra estos mismos comandos:

aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin 730335573515.dkr.ecr.us-east-1.amazonaws.com

docker tag <imagen-local>:<tag> 730335573515.dkr.ecr.us-east-1.amazonaws.com/forms-docker:<tag>
docker push 730335573515.dkr.ecr.us-east-1.amazonaws.com/forms-docker:<tag>

En la pestaña Imágenes quedan las versiones subidas (latest, r1, r2, ~11 GB cada una). Anotar el digest (sha256:…) de la versión a desplegar: la task definition lo referencia por digest.

1.2 · Security group forms-sg-ecs

Un security group es el firewall virtual que AWS aplica a cada tarea Fargate (a su interfaz de red). Define qué tráfico puede entrar y salir del contenedor. forms-sg-ecs lo comparten admin, forms y reports: abre la consola WebLogic hacia afuera, permite que los contenedores se hablen entre sí y deja salir el tráfico hacia ECR, CloudWatch, EFS y la base de datos.

EC2 → Red y seguridad → Grupos de seguridad → Crear grupo de seguridad, en la VPC vpc-055a4007418b34e64 (vpc-Banesco-Seguros-VE-dev).

1.3 · EFS rector-dev y NFS 2049

Amazon EFS (Elastic File System) es un sistema de archivos de red (NFS) administrado por AWS. Las tareas Fargate son efímeras: todo lo que se escribe dentro del contenedor se pierde al detenerse. Por eso el dominio WebLogic (forms_domain), las aplicaciones y los scripts viven en el EFS y se montan en cada contenedor. Así admin, forms y reports comparten el mismo dominio y los cambios sobreviven a los redespliegues.

Amazon EFS → Sistemas de archivos → rector-dev (fs-08471cc88d2a8edc3). Debe estar Disponible y con mount target en la AZ de pub-A (us-east-1a / subnet-01212efd4a9ce759b).

1.3d · Regla NFS 2049 en el SG del EFS

NFS usa el puerto TCP 2049. Para que una tarea monte el EFS, el SG de los mount targets (ESF-dev-sg) debe aceptar conexiones a ese puerto desde el SG de las tareas (forms-sg-ecs). Usar el SG como origen (en lugar de IPs) permite que cualquier tarea nueva, con cualquier IP, pueda montar el filesystem.

  1. EC2 → Grupos de seguridad → sg-0e39a7aa49ff6a22b (ESF-dev-sg)
  2. Pestaña Reglas de entrada: debe existir NFS / TCP 2049 con origen forms-sg-ecs (sg-0e1787d32bac71fcd)
  3. Confirmar (fuera de consola) los directorios domain_forms/domains, app y scripts/admin bajo /aws-backup-restore_2020-04-19T22-54-07-041Z
Sin esta regla, la tarea falla con mount.nfs4: Connection timed out. En la captura hay varias reglas NFS 2049; la crítica para ECS Forms es la del origen sg-0e1787d32bac71fcd.

1.5 · Cloud Map — namespace forms.localHecho

AWS Cloud Map es el servicio de descubrimiento de servicios de AWS: mantiene un registro de nombres DNS que apuntan a las IPs de las tareas ECS. En Fargate cada tarea recibe una IP distinta en cada despliegue, por lo que los contenedores no pueden referenciarse por IP. Con Cloud Map, forms y reports encuentran al AdminServer por un nombre fijo (weblogic-admin.forms.local) y ECS actualiza la IP detrás de ese nombre automáticamente.

Namespace DNS privado que comparten admin, forms y reports. Se crea una sola vez y solo depende de la VPC, así que puede hacerse antes del cluster y de la task definition. Service Discovery (weblogic-admin) se asocia después, al crear el servicio en el Paso 4.

1.5a · Crear espacio de nombres

Un espacio de nombres (namespace) es el dominio DNS bajo el que se registran los servicios; aquí forms.local. Cada servicio ECS con Service Discovery agrega un nombre dentro de él (weblogic-admin.forms.local, etc.).

AWS Cloud Map → Espacios de nombres → Crear espacio de nombres.

1.5b · Configuración del namespace

El tipo Llamadas a la API y consultas de DNS en VPC crea un DNS privado: los nombres solo se resuelven desde dentro de la VPC indicada, no desde Internet. El TTL es el tiempo (en segundos) que los clientes guardan en caché una respuesta DNS; un valor bajo (15 s) hace que un cambio de IP de la tarea se note rápido.

2 Cluster forms_reportHecho

Un cluster ECS es la agrupación lógica donde se ejecutan los servicios y tareas. No es una máquina: con Fargate AWS provee y administra la infraestructura de cómputo de cada tarea, sin servidores EC2 que mantener. El cluster forms_report agrupa los tres servicios (admin, forms y reports) del dominio, lo que facilita verlos, monitorearlos y administrarlos juntos.

  1. ECS → Clústeres → Crear clúster
  2. Nombre del clúster: forms_report
  3. Espacio de nombres predeterminado: dejar vacío (el namespace forms.local se asocia en el Paso 4)
  4. Infraestructura: Solo Fargate
  5. Monitoreo, cifrado y etiquetas: valores por defecto → Crear

Al crearlo, la página del cluster muestra el estado Activo. Los contadores de servicios y tareas quedan en 0 hasta crear los servicios; con admin, forms y reports desplegados se ven 3 servicios activos y 3 tareas en ejecución, como en la captura.

3 Crear task definition AdminServerHecho

La task definition (definición de tarea) es la plantilla que describe cómo ejecutar el contenedor: imagen, CPU y memoria, puertos, variables de entorno, comando de arranque, volúmenes EFS, logs y roles IAM. Es el equivalente en ECS de un docker-compose.yml. Es inmutable: cada cambio genera una nueva revisión numerada (forms-admin:1, :2, …) y el servicio indica qué revisión ejecutar.

Definición completa de la última revisión en el anexo JSON (forms-admin:7).

ECS → Definiciones de tareas → Crear nueva definición de tarea (o Crear nueva revisión si la familia ya existe). Familia: forms-admin. Los subpasos siguientes siguen el orden del asistente de la consola.

3.6 · Almacenamiento efímero + volúmenes EFS

El almacenamiento efímero es el disco local de la tarea: aloja la imagen descomprimida y lo que se escriba fuera de los volúmenes, y se borra al detenerse la tarea. Los volúmenes EFS declaran qué carpetas del EFS (Paso 1.3) se ponen a disposición del contenedor; son persistentes y compartidas. Cada volumen apunta a un directorio raíz dentro del filesystem, de modo que el contenedor solo ve esa parte.

Almacenamiento efímero: 100 GiB (el valor por defecto de 20 GiB no alcanza para extraer la imagen).

Tres volúmenes EFS, tipo EFS, filesystem rector-dev (fs-08471cc88d2a8edc3), punto de acceso Ninguno. En Configuraciones avanzadas dejar cifrado en tránsito habilitado.

4.10 · Ruta hacia la BD

La base de datos Oracle (192.168.229.137) está en otra red, alcanzable por una interconexión de VPC (peering pcx-0ad20c217472c7080). La subnet pub-A envía por defecto todo el tráfico al Internet Gateway, así que sin una ruta específica las conexiones a la BD terminan en ORA-12170 (timeout). Se agrega una ruta /32 hacia el peering en la tabla de rutas de pub-A (Pub-RT). La tabla es compartida: se hace una sola vez y sirve para admin, forms y reports.

No hace falta asociar la subnet privada database-A al servicio. Si se asocian pub-A y database-A, ECS puede colocar la tarea en la privada: la IP pública queda asignada pero no responde desde Internet (su ruta por defecto es NAT, no IGW).
  1. VPC → Subredes → pub-A (subnet-01212efd4a9ce759b).
  2. Pestaña Tabla de enrutamiento → abrir rtb-0a99542c9d91cd2cc (…-Pub-RT).

6 Alinear hostnames Cloud MapPendiente

El dominio forms_domain se creó y probó en local con Docker Compose. Allí cada contenedor se localiza por su nombre corto de servicio (weblogic-admin, weblogic-forms, weblogic-reports), que el DNS interno de Docker resuelve automáticamente. Esos nombres quedaron guardados en la configuración del dominio: como dirección de cada Machine de WebLogic y como dirección de escucha de cada Node Manager.

En ECS Fargate ese DNS de Docker no existe. Los únicos nombres que resuelven son los que registra Cloud Map (Paso 1.5), y siempre son nombres completos (FQDN) del namespace: weblogic-admin.forms.local. Un nombre corto no resuelve dentro de la VPC. Sin este ajuste:

  • El AdminServer no puede contactar al Node Manager de los contenedores forms y reports, y por tanto no puede arrancar ni controlar WLS_FORMS y WLS_REPORTS.
  • Cada Node Manager intenta escuchar en un hostname que no resuelve.

6a · Qué cambia el script

set-cloudmap-hostnames.sh agrega el sufijo .forms.local a los nombres cortos en los archivos del dominio (en el EFS):

ArchivoAntesDespués
config/config.xml (Machine AdminServerMachine)weblogic-adminweblogic-admin.forms.local
config/config.xml (Machine FormsMachine)weblogic-formsweblogic-forms.forms.local
config/config.xml (Machine ReportsMachine)weblogic-reportsweblogic-reports.forms.local
nodemanager/nodemanager.propertiesListenAddress=weblogic-adminListenAddress=weblogic-admin.forms.local
nodemanager_forms/nodemanager.propertiesListenAddress=weblogic-formsListenAddress=weblogic-forms.forms.local
nodemanager_reports/nodemanager.propertiesListenAddress=weblogic-reportsListenAddress=weblogic-reports.forms.local

Además:

  • Respalda cada archivo que modifica (config.xml.bak_<fecha>, nodemanager.properties.bak_<fecha>).
  • Si hay cambios de consola sin activar en pending/, los aparta a pending.bak_<fecha> para que no reescriban config.xml.
  • Es idempotente: los valores que ya tienen el sufijo no se tocan, por lo que puede ejecutarse más de una vez.
  • Se niega a ejecutarse si detecta un servidor WebLogic corriendo en el contenedor.
  • Al final muestra el estado y falla si quedó algún nombre corto en config.xml.

6b · Cuándo y cómo aplicarlo

El AdminServer, WLS_FORMS y WLS_REPORTS deben estar detenidos en todos los contenedores: un AdminServer en ejecución reescribe config.xml con su copia en memoria y se pierde el cambio. Por eso lo ideal es aplicarlo antes del Paso 7, con el contenedor en sleep infinity. Si el AdminServer ya está arriba, detenerlo, aplicar el script y volver a arrancarlo.

Como el dominio está en el EFS (persistente y compartido), se hace una sola vez: admin, forms y reports ven el dominio corregido. Desde la sesión ECS Exec (Paso 5), como oracle: 

/u01/oracle/scripts/set-cloudmap-hostnames.sh --check   # solo muestra el estado actual, no cambia nada
/u01/oracle/scripts/set-cloudmap-hostnames.sh           # respalda y cambia a *.forms.local

Con --check se ve si ya está aplicado: si aparecen weblogic-admin, weblogic-forms o weblogic-reports sin .forms.local, falta aplicarlo. El resultado esperado es ✓ Dominio alineado con Cloud Map (*.forms.local).

MachineFQDNNode Manager
AdminServerMachineweblogic-admin.forms.localnodemanager/
FormsMachineweblogic-forms.forms.localnodemanager_forms/
ReportsMachineweblogic-reports.forms.localnodemanager_reports/
Los FQDN solo resuelven si cada servicio ECS tiene Service Discovery con ese nombre: weblogic-admin (Paso 4), y weblogic-forms / weblogic-reports en sus fases. Verificar con getent hosts weblogic-admin.forms.local.

7 Arrancar AdminServer y consolaPendiente

Desde la sesión ECS Exec del Paso 5 (usuario oracle), ejecutar el script de arranque. Inicia el Node Manager y luego el AdminServer:

7a · Arranque del AdminServerHecho

El script muestra el modo, las variables (DOMAIN_HOME, ADMIN_PORT 7001), arranca el Node Manager en el puerto 5556, limpia los .lok de ejecuciones anteriores y lanza startWebLogic.sh. La salida de WebLogic no se muestra en consola: va a servers/AdminServer/logs/AdminServer.out y el script indica dónde consultar el log.

En modo normal WebLogic queda ligado a la sesión ECS Exec: al cerrarla se detiene el AdminServer. Para que siga corriendo tras salir de la sesión, usar ./startAdminserver.sh -keep.

7b · Monitorear el log hasta RUNNINGHecho

7d · Arranque automático del AdminServer al iniciar la tareaHecho

Una vez validado el arranque manual, se cambia el comando del contenedor para que la tarea inicie el AdminServer sin intervención. El cambio se hace creando una nueva revisión de la task definition y actualizando el servicio para que la use.

  1. ECS → Definiciones de tareas → forms-admin → seleccionar la última revisión → Crear nueva revisión.
  2. Contenedor admin → Configuración de Docker:
    • Punto de entrada: vacío.
    • Comando: /u01/oracle/scripts/startAdminserver.sh,-keep (reemplaza a sleep,infinity).
  3. Crear → queda una nueva revisión (forms-admin:N).
  4. ECS → cluster forms_report → servicio admin → Actualizar → revisión forms-admin:N → marcar Forzar nueva implementación → Actualizar.
  5. Esperar la nueva tarea en Ejecutando y validar RUNNING con el log (7b).

Equivalente en el JSON de la task definition:

"command": ["/u01/oracle/scripts/startAdminserver.sh", "-keep"]
ComandoComportamiento
/u01/oracle/scripts/startAdminserver.sh,-keepLa tarea sigue viva aunque el AdminServer falle: permite entrar por ECS Exec a revisar. ECS no detecta la caída de WebLogic.
/u01/oracle/scripts/startAdminserver.shSi el AdminServer termina, la tarea termina y el servicio lanza otra: recuperación automática.
El script se ejecuta desde el EFS (/u01/oracle/scripts): debe existir allí con permiso de ejecución (chmod +x startAdminserver.sh); si no, la tarea se detiene al arrancar. La salida de WebLogic no va a CloudWatch (/ecs/forms-admin), solo los mensajes del script: el log se consulta en AdminServer.log como en 7b.
Con el arranque automático ya no hace falta ejecutar ./startAdminserver.sh desde ECS Exec; la sesión (Paso 5) se sigue usando para revisar logs y diagnosticar.

Anexo Comandos AWS CLIHecho

La creación se hizo por consola; la CLI sirve para exportar configuración, diagnosticar red / ECR / EFS y ECS Exec. Los comandos de infraestructura (subnets, SG, EFS) son comunes a admin, forms y reports; para los servicios basta cambiar SERVICE y la task definition. 

export AWS_REGION=us-east-1
export CLUSTER=forms_report
export SERVICE=admin            # forms-server / reports-server en las otras fases
export TASKDEF=forms-admin:6

1 · Exportar servicio y task definition

Respaldar y revisar red, SG, IP pública y definición de tarea.

aws ecs describe-services --cluster $CLUSTER --services $SERVICE \
  --query 'services[0].{status:status,running:runningCount,td:taskDefinition,net:networkConfiguration,exec:enableExecuteCommand}'

aws ecs describe-task-definition --task-definition $TASKDEF \
  --query taskDefinition --output json > conf_json/forms-admin.json

2 · Subnets y rutas (Internet / BD)

Verificar pub-A (IGW + ruta a la BD, Paso 4.10). Útil ante timeout de ECR u ORA-12170.

aws ec2 describe-subnets --subnet-ids subnet-01212efd4a9ce759b subnet-0f4dc6c60b100a66d \
  --query 'Subnets[*].{Id:SubnetId,Name:Tags[?Key==`Name`].Value|[0],Public:MapPublicIpOnLaunch,Az:AvailabilityZone}' \
  --output table

# Rutas de pub-A: debe incluir 192.168.229.137/32 → pcx y 0.0.0.0/0 → igw
aws ec2 describe-route-tables \
  --filters Name=association.subnet-id,Values=subnet-01212efd4a9ce759b \
  --query 'RouteTables[0].Routes[*].{Dest:DestinationCidrBlock,Gw:GatewayId,Pcx:VpcPeeringConnectionId,Nat:NatGatewayId,State:State}' \
  --output table

3 · Security groups

Reglas de entrada/salida del SG de las tareas (Paso 1.2) y del EFS (Paso 1.3).

aws ec2 describe-security-groups --group-ids sg-0e1787d32bac71fcd   # forms-sg-ecs
aws ec2 describe-security-groups --group-ids sg-0e39a7aa49ff6a22b   # ESF-dev-sg
El SG default | DO NOT USE (sg-04963b231db91fcf1) no tiene reglas de entrada ni de salida: no usarlo en servicios ECS.

4 · EFS: mount targets y NFS 2049

★ Lecciones críticas

Errores encontrados al crear el servicio, en el orden en que aparecieron:

  1. ECS Exec sin rol de tarea (Paso 1.4) — el servicio no permite activar Exec; crear ecs-forms-admin-task-role y una nueva revisión.
  2. Timeout hacia ECR (Pasos 1.2 y 4.9) — GetAuthorizationToken … i/o timeout: subnet sin salida a internet o SG default sin egress. Usar solo pub-A, IP pública y forms-sg-ecs.
  3. Espacio efímero (Paso 3.6) — no space left on device al extraer la imagen; subir a 100 GiB.
  4. EFS NFS 2049 (Paso 1.3) — mount.nfs4: Connection timed out: el SG del EFS debe aceptar 2049 desde forms-sg-ecs.
  5. Rutas EFS (Paso 3.6–3.7) — No such file or directory: rootDirectory sin el prefijo erróneo /domain.
  6. Comando sleep infinity (Paso 3.5) — permite ECS Exec y arranque manual; no redefinir PATH.
  7. Service Discovery (Paso 4.6) — solo al crear el servicio; requiere el namespace del Paso 1.5; los demás contenedores dependen de weblogic-admin.forms.local.
  8. Solo pub-A + ruta BD (Paso 4.9–4.10) — no asociar database-A; 192.168.229.137/32 → pcx en Pub-RT.
  9. Hostnames (Paso 6) — sin FQDN en config.xml y nodemanager.properties aparece UnknownHostException.
  10. ECS Running ≠ WebLogic RUNNING (Paso 7) — validar siempre el log del AdminServer.
