Lecciones críticas, 2: el comando sleep infinity permite que la tarea ECS quede RUNNING sin arrancar WebLogic automáticamente, para entrar con ECS Exec y lanzar el entrypoint / AdminServer / WLS_FORMS a mano mientras DNS, dominio y red no están listos. 8 RedesHecho

Topología recomendada del servicio (admin / forms / reports): solo la subnet pública pub-A (ECR, IP pública, consola HTTP) más la ruta a Oracle en la route table Pub-RT (Paso 8c).

NO es necesario asociar la subnet privada database-A al servicio ECS. Con la ruta 192.168.229.137/32 → pcx-… en Pub-RT las tareas en pub-A alcanzan la BD. Si se asocian pub-A + database-A, ECS puede colocar la tarea en la privada: la IP pública queda asignada pero no responde desde Internet (default route = NAT, no IGW).

Agregar solo esta subnet al servicio ECS.

b. Subnet privada database-A (referencia; no asociar al servicio)

database-A (subnet-0f4dc6c60b100a66d) ya tenía la ruta a Oracle en Priv-C-RT. Sirve como referencia del peering, pero no hace falta listarla en la configuración de red del servicio ECS: el acceso a BD se obtiene replicando esa ruta en Pub-RT (punto c).

  • ID: subnet-0f4dc6c60b100a66d
  • Nombre: vpc-Banesco-Seguros-VE-dev-database-A-SN
  • Route table: rtb-09c278a96f73d2b4c (…-Priv-C-RT) — 192.168.229.137/32 → pcx-… + NAT

Configuración de red del servicio

Si el servicio incluye ambas subnets, ECS elige una al azar. En database-A (NAT) la consola/Forms por IP pública no responde aunque AdminServer escuche en :7001 dentro del contenedor. Usar solo pub-A.

c. Modificar route table de pub-A (ruta a la BD — suficiente para Oracle)

Este paso es el que sustituye la necesidad de asociar database-A. En Pub-RT agregar destino 192.168.229.137/32 vía la misma interconexión peering que ya usa database-A.

  1. VPC → Subredes → buscar pub-A / subnet-01212efd4a9ce759b
  2. Pestaña Tabla de enrutamiento → clic en rtb-0a99542c9d91cd2cc
  3. Editar rutas → Agregar ruta:
    • Destino: 192.168.229.137/32
    • Target: Interconexión → pcx-0ad20c217472c7080
  4. Guardar cambios (estado Activo)

Apertura de puerto 9001 en el Security Group (sesión separada)

12 Impacto del DNS Cloud Map (weblogic-admin → weblogic-admin.forms.local)Hecho

Si se aplicó Paso 0 — nombres Cloud Map (set-cloudmap-hostnames.sh), este paso queda como verificación y referencia del problema; no hay que editar nada a mano.

En docker-compose, el hostname corto weblogic-admin lo resuelve la red interna de Docker. Con ECS Service Discovery + AWS Cloud Map (namespace forms.local), el nombre registrado es el FQDN: 

weblogic-admin.forms.local

El short name weblogic-admin no resuelve solo dentro de la VPC (salvo search domain o /etc/hosts). Si el dominio Forms/Reports se creó con hostnames de compose, NodeManager y AdminServer fallan al arrancar.

12a. Síntoma observado

java.net.UnknownHostException: weblogic-admin: Name or service not known
<SEVERE> <Fatal error in NodeManager server>

NodeManager no puede hacer bind/listen → procesos java / startWebLogic.sh terminan (zombies) y la consola en :7001 no responde, aunque el contenedor ECS siga RUNNING (sleep infinity).

12b. Archivos del dominio que debieron modificarse

En el dominio montado por EFS (ruta contenedor /u01/oracle/user_projects/domains/forms_domain) se actualizó el listen address de weblogic-admin a weblogic-admin.forms.local al menos en:

Archivo (ruta completa en el contenedor)Cambio
/u01/oracle/user_projects/domains/forms_domain/nodemanager/nodemanager.properties ListenAddress=weblogic-admin.forms.local
/u01/oracle/user_projects/domains/forms_domain/config/config.xml <listen-address>weblogic-admin.forms.local</listen-address> (AdminServer / Machine según el dominio)
Otros archivos pueden referenciar el FQDN tras el ajuste (p. ej. EM .../config/fmwconfig/servers/AdminServer/applications/em/META-INF/emoms.properties). Lo crítico para el arranque es NodeManager + config.xml.

Auditoría rápida antes de arrancar:

grep -RIn --exclude-dir=tmp --exclude-dir=cache --exclude='*.log' \
  -E 'weblogic-admin' \
  "$DOMAIN_HOME/nodemanager" "$DOMAIN_HOME/config" /u01/oracle/scripts 2>/dev/null | head -80

getent hosts weblogic-admin.forms.local
# Debe coincidir con la IP VPC de la tarea (p. ej. eth1), NO con eth0 169.254.x.x
ip -4 -o addr show | awk '{print $2,$4}'

12d. Cómo evitarlo desde el diseño del dominio

Prevención: este problema se puede evitar si la configuración del dominio Forms/Reports se hace desde el origen (creación del dominio / docker-compose) usando el sufijo .forms.local en los nombres de host de los servidores, de modo que coincidan con el DNS que generará Cloud Map en ECS.
En docker-compose / dominioEquivalente Cloud Map (namespace forms.local)

weblogic-forms.forms.localservicio Discovery weblogic-forms

Así, nodemanager.properties, config.xml, Machines y ADMIN_SERVER_HOST ya apuntan al FQDN y no hace falta reescribir el dominio al pasar de compose a ECS. Si el dominio ya existe con short names, el remapeo a *.forms.local es obligatorio antes de un arranque estable en AWS: usar /u01/oracle/scripts/set-cloudmap-hostnames.sh (Paso 0).

Anexo Verificación de red hacia BDHecho

Ante errores tipo ORA-12170 (TCP connect timeout) desde el contenedor hacia Oracle (ej. 192.168.229.137:1521), estos comandos permiten descartar Task Definition y Security Group antes de escalar a soporte de redes.

La Task Definition no define reglas de firewall. La red la define el servicio ECS (VPC, subnets, SG, IP pública) + route tables / NACL / VPN en la VPC.

1. Red del servicio ECS

Función: listar subnets, SG e IP pública del servicio.

aws ecs describe-services \
  --cluster forms_report \
  --services forms-admin \
  --region us-east-1 \
  --query 'services[0].networkConfiguration' \
  --output json

Equivale para Forms: --services forms-server.

2. Egress del Security Group de la tarea

Función: confirmar que el SG no bloquea salida (p. ej. TCP 1521).

aws ec2 describe-security-groups \
  --group-ids sg-0e1787d32bac71fcd \
  --region us-east-1 \
  --query 'SecurityGroups[0].IpPermissionsEgress' \
  --output json
Si egress es All traffic a 0.0.0.0/0, se descarta el SG de la tarea como causa del timeout a Oracle.

3. Route table de pub-A (suficiente para BD)

Función: confirmar ruta 192.168.229.137/32 → pcx-… en Pub-RT (Paso 8c). Con eso no hace falta asociar database-A al servicio.

aws ec2 describe-route-tables \
  --filters Name=association.subnet-id,Values=subnet-01212efd4a9ce759b \
  --region us-east-1 \
  --query 'RouteTables[0].Routes[*].{Dest:DestinationCidrBlock,Gw:GatewayId,Pcx:VpcPeeringConnectionId,Nat:NatGatewayId,State:State}' \
  --output table
Antes del Paso 8c: en pub-A el tráfico a 192.168.229.137:1521 caía en la ruta default al IGW → ORA-12170. Con la ruta /32 vía peering, la tarea en pub-A alcanza la BD sin asociar database-A. Si la tarea cae en database-A, la IP pública no responde desde Internet (NAT).

4. Prueba desde el contenedor (evidencia)

Además del test TCP, se puede validar con sqlplus desde el contenedor. En la práctica, sqlplus falló hasta instalar la librería libaio (dependencia nativa de cliente Oracle Instant Client / tools en ORACLE_HOME).

libaio debe ir en la imagen Docker (Dockerfile / build), no instalarse “a mano” en cada tarea Fargate. El filesystem del contenedor es efímero: lo que se instala con yum/microdnf/apt en una sesión ECS Exec se pierde al recrear la tarea. Incluir libaio (p. ej. paquete libaio / libaio1) en la creación de la imagen ECR (forms-docker) y regenerar/pushear la imagen antes de redesplegar.

Instalación temporal solo para una prueba puntual (no persistente):

# Ejemplo Oracle Linux / RHEL (dentro del contenedor, como root)
# yum install -y libaio
# o: microdnf install -y libaio

Pruebas de conectividad:

# TCP (no requiere libaio)
timeout 5 bash -c 'echo >/dev/tcp/192.168.229.137/1521' && echo OK || echo FAIL

# sqlplus (requiere libaio en la imagen)
$ORACLE_HOME/bin/sqlplus USUARIO/PASS@192.168.229.137:1521/METAPRD
Un timeout confirma que el paquete no llega al listener (routing/firewall del destino), no necesariamente usuario/password incorrectos. Si sqlplus falla por libaio.so.1: cannot open shared object file, falta el paquete en la imagen.

★ Lecciones críticas

  1. Espacio efímero Fargate (Paso 4) — imagen grande → no space left on device; ephemeral ~100 GiB.
  2. Comando sleep infinity (Paso 3d) — permite ECS Exec y arranque manual mientras DNS/dominio no están listos. Configurar entrypoint sh,-c + comando sleep,infinity. No redefinir PATH en la Task Definition sin rutas de sistema (rompe sleep).
  3. libaio / net-tools / nano en la imagen (build Dockerfile / ECR) — libaio hace falta para sqlplus / cliente Oracle; net-tools y nano ayudan en diagnóstico/edición dentro del contenedor. No instalarlos solo con ECS Exec: el filesystem es efímero y se pierde al recrear la tarea. Deben ir en la creación de la imagen y regenerar/pushear a ECR.
  4. SG + egress (Paso 8 / SG) — evitar SG default sin salida (timeout ECR); usar forms-sg-ecs.
  5. EFS NFS 2049 (anexo CLI) — SG del EFS debe permitir 2049 desde el SG de ECS.
  6. Rutas EFS (Paso 4–5) — rootDirectory sin prefijo erróneo /domain.
  7. Solo pub-A en el servicio (Paso 8) — no asociar database-A; si la tarea cae en privada, la IP pública no responde (NAT ≠ IGW).
  8. Ruta BD en Pub-RT (Paso 8c) — 192.168.229.137/32 → pcx basta para Oracle desde pub-A.
  9. DNS / Service Discovery (Pasos 10–12):
    • Compose resuelve short names (weblogic-admin); Cloud Map expone el FQDN weblogic-admin.forms.local.
    • El short name no resuelve solo en la VPC (salvo search domain o /etc/hosts).
    • Alinear dominio: .../nodemanager/nodemanager.properties (ListenAddress) y .../config/config.xml (listen-address) al FQDN; si no → UnknownHostException / zombies.
    • Service Discovery se asocia al crear el servicio ECS (no con un update simple).
    • Validar getent hosts …forms.local = IP VPC de la tarea (eth1), no eth0 169.254… (ECS Exec).
    • Forms/Reports: Machines / Coherence WKA (weblogic-forms, weblogic-reports) también necesitan Discovery o FQDN. Hacerlo desde el inicio con set-cloudmap-hostnames.sh (Paso 0); un short name sin resolver deja a ese managed fuera del WKA y no arranca si el otro managed no responde.
    • Regla interna del SG Todo el tráfico (no solo TCP): Coherence descubre miembros por UDP 7574.
    • Task def Forms: ADMIN_SERVER_HOST=weblogic-admin.forms.local (Paso 3).
    • Prevención en compose / nuevo dominio: si se crea una nueva imagen o dominio con docker-compose, definir los hostnames de contenedores ya con el sufijo del namespace (ej. weblogic-admin.forms.local, weblogic-forms.forms.local), de modo que coincidan con Cloud Map y no sea necesario modificar después nodemanager.properties, config.xml ni otros archivos del dominio.
  10. ECS RUNNING ≠ WebLogic RUNNING (Paso 9) — PID 1 puede ser sleep infinity con Java muerto.
  11. Zombies <defunct> — ya están muertos; no se limpian con kill si el padre es sleep infinity.
  12. Consola / Forms por IP pública (Paso 8) — solo fiable en pub-A + SG 7001/9001.
  13. “Inaccessible” en Remote Console — a menudo Admin ↔ managed (DNS/JMX), no que el managed esté caído.
  14. FRM-93500 — el JNLP llega al servlet; falla el runtime frmweb en el servidor (default.env, libs, paths).
  15. Cliente JNLP en Linux — JDK 8 x64 + javaws (IcedTea/OpenWebStart); JDK 17 no trae JWS.
  16. ECS Exec (Paso 9) — Session Manager Plugin + task role SSM.
  17. Redeploy — nueva tarea = nueva IP; Cloud Map se actualiza (respetar TTL).
  18. TCP 1521 hacia Oracle — validar también firewall/SG del listener, no solo la VPC.
  19. URL de BD quemada en el dominio — pendiente por resolver. Al crear el dominio (wizard WebLogic 14.1.2), la URL JDBC queda fija en archivos como config/fmwconfig/jps-config-jse.xml, config/jdbc/opss-datasource-jdbc.xml, config/jdbc/WLSRuntimeSchemaDataSource-jdbc.xml y otros. WebLogic no resuelve variables de entorno de forma nativa en esos XML. Objetivo: parametrizar la URL (y alinear bootstrap OPSS si aplica) vía env en el contenedor (entrypoint con sed/envsubst o WLST offline) al lanzar la tarea, sin reeditar el dominio a mano por entorno.
  20. Usuario oracle en la ejecución (Paso 9 / ECS Exec) — la ejecución de los contenedores (arranque de AdminServer / WLS_FORMS, scripts y shell interactivo) debe realizarse con el usuario oracle, para que se inicialicen / apliquen correctamente las variables de entorno definidas en la Task Definition asociada al servicio (p. ej. JAVA_OPTIONS, ADMIN_SERVER_HOST, DOMAIN_HOME). En ECS Exec: 
    aws ecs execute-command \
  --cluster forms_report \
  --task <TASK_ID> \
  --container forms-server \
  --interactive \
  --command "su - oracle"
    (Equivalente para admin: --container admin.) Evitar trabajar como root para el arranque de WebLogic.
  21. Arranque automatizado de WLS_FORMS — crear servers/WLS_FORMS/security/boot.properties dentro del dominio ($DOMAIN_HOME/servers/WLS_FORMS/security/boot.properties): 
    username=weblogic
password=<clave>
    En el primer arranque WebLogic encripta el archivo; startManagedWebLogic.sh deja de pedir credenciales. Las variables ADMIN_USER / ADMIN_PASSWORD del docker-compose no bastan por sí solas (el entrypoint no las usa al arrancar el managed server). Tampoco sirve export WLS_USER / WLS_PW antes del script: startManagedWebLogic.sh las reinicia vacías. Usar boot.properties en security/ del managed server (no confundir con el de Node Manager bajo .../data/nodemanager/).
