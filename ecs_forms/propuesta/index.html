Arquitectura contenedores WebLogic Forms & Reports en AWS ECS — RECTOR

La presente propuesta describe el proyecto para modernizar el despliegue del aplicativo RECTOR (Oracle Forms & Reports 14.1.2 sobre WebLogic), migrando desde una arquitectura monolítica tradicional hacia una arquitectura distribuida en contenedores, primero validada en Docker Compose y luego operada en Amazon ECS Fargate con almacenamiento compartido en Amazon EFS y conectividad a Oracle Database 19c.

El alcance comprende la construcción de imágenes Docker, la orquestación del dominio WebLogic distribuido (AdminServer, WLS_FORMS, WLS_REPORTS), la publicación en Amazon ECR, la creación de servicios ECS y la puesta en marcha operativa con acceso a la base de datos corporativa, preservando la funcionalidad del negocio sobre RECTOR.

1

Alcance del proyecto — Arquitectura objetivo

Se implementará un dominio WebLogic 14.1.2 distribuido para Oracle Forms & Reports, separando responsabilidades en contenedores independientes que comparten el mismo dominio y aplicaciones mediante volúmenes persistentes. La solución contempla los siguientes componentes:

Componente Hostname / Servicio Función Puertos clave
AdminServer weblogic-admin / weblogic-admin.forms.local Administración central del dominio, Node Manager y OHS (proxy/balanceo) 7001, 5556, 7777, 4443
WLS_FORMS weblogic-forms / weblogic-forms.forms.local Ejecución de módulos Oracle Forms del aplicativo RECTOR 9001, 9501, 9991, 5556
WLS_REPORTS weblogic-reports / weblogic-reports.forms.local Generación y distribución de reportes Oracle Reports 9012, 9512, 9992, 5556
Almacenamiento EFS rector-dev (AWS) Dominio, aplicaciones y scripts compartidos entre contenedores NFS 2049
Base de datos Oracle 19c Persistencia de datos del sistema RECTOR 1521

Diagrama 1 — Arquitectura local (Docker Compose)

Dominio WebLogic distribuido en contenedores Docker

Diagrama 2 — Arquitectura en AWS (ECS Fargate)

Despliegue en cluster ECS forms_report con EFS, ECR y Cloud Map

La imagen base image_forms_14.1.2 (Oracle WebLogic 14.1.2 con Forms & Reports) se reutiliza en los tres contenedores. El dominio forms_domain se monta de forma compartida, permitiendo administración centralizada con ejecución distribuida. En AWS, los hostnames se alinean con el namespace DNS privado forms.local (Cloud Map) para garantizar la resolución entre AdminServer y Managed Servers sin depender de IPs fijas.

2

Etapas del proyecto

El proyecto se ejecutará en fases secuenciales, validando cada componente en entorno local antes de su despliegue en la nube:

a

Creación y configuración de imágenes en Docker Compose

Construcción de la imagen Docker image_forms_14.1.2 a partir de Oracle WebLogic 14.1.2 con Forms & Reports. Inclusión de dependencias operativas (libaio, net-tools, herramientas de diagnóstico). Desarrollo de scripts de entrypoint por rol (admin, forms, reports). Definición del archivo docker-compose.yml con red weblogic-network, variables de entorno, mapeo de puertos y health checks.

  • Dockerfile y scripts de arranque (entrypoint.sh, startNodeManager.sh)
  • Configuración de hostnames con sufijo .forms.local para compatibilidad futura con Cloud Map
  • Volúmenes bind mount: domains/, app/, scripts/
b

Despliegue de arquitectura en Docker Compose

Levantamiento y validación del stack completo en entorno local: AdminServer con Node Manager y OHS, WLS_FORMS y WLS_REPORTS como Managed Servers. Verificación de comunicación T3 entre contenedores, arranque de clusters cluster_forms y cluster_reports, y acceso a consolas WebLogic, Forms y Reports.

  • Secuencia de arranque: Node Manager → AdminServer → Managed Servers
  • Validación de puertos HTTP/HTTPS y Node Manager por máquina
  • Pruebas funcionales del aplicativo RECTOR en entorno containerizado
c

Carga y configuración de imagen Docker en AWS

Publicación de la imagen validada en Amazon ECR (forms-docker). Configuración de roles IAM (ecsTaskExecutionRole, ecs-forms-admin-task-role), security groups (forms-sg-ecs), reglas NFS hacia EFS y almacenamiento efímero Fargate (~100 GiB) para imágenes de gran tamaño.

  • Push de imagen a ECR y verificación de pull desde subnets ECS
  • Configuración de logs en CloudWatch (/ecs/forms-admin, /ecs/forms-server)
  • Habilitación de ECS Exec para diagnóstico remoto
d

Creación de contenedores: AdminServer, Forms Server y Report Server

Creación del cluster ECS forms_report y de las task definitions y servicios para cada rol: forms-admin, forms-server y reports-server. Configuración de Fargate (2 vCPU, 4 GB), variables de entorno y puertos. Los contenedores se integran mediante AWS Service Discovery (Cloud Map) en el namespace DNS forms.local, de modo que AdminServer, Forms y Reports se comunican por nombres de host —por ejemplo weblogic-admin.forms.local— dentro del subdominio creado, sin depender de direcciones IP fijas aunque las tareas ECS se recreen o cambien de red.

  • Service Discovery: registro automático de servicios (weblogic-admin, weblogic-forms, weblogic-reports) con resolución DNS privada en VPC; comunicación estable basada en FQDN
  • Task definitions con imagen ECR, comandos y secrets (migración a Secrets Manager)
  • Red: subnet pública pub-A, IP pública habilitada, SG con puertos 7001/9001/9012
  • Ruta VPC Peering hacia Oracle (192.168.229.137/32) en Pub-RT
e

Carga de copia de dominio para ser compartido por los contenedores

Restauración del dominio WebLogic forms_domain y aplicaciones RECTOR en Amazon EFS (rector-dev). Montaje de volúmenes efs-domains, efs-app y efs-scripts en las rutas del contenedor. Ajuste de nodemanager.properties y config.xml para hostnames FQDN (*.forms.local).

  • Paths EFS: domain_forms/domains, domain_forms/app, domain_forms/scripts
  • Mount points: /u01/oracle/user_projects/domains, apps, scripts
  • Verificación de montajes NFS y permisos entre servicios ECS
f

Ejecución de contenedores con acceso a Base de Datos Oracle 19c

Puesta en marcha operativa de AdminServer, WLS_FORMS y WLS_REPORTS en ECS con conectividad JDBC hacia Oracle Database 19c. Validación de red (TCP 1521), pruebas con sqlplus, arranque estable de Managed Servers y verificación funcional del aplicativo RECTOR (Forms y Reports) contra la base de datos de producción/desarrollo.

  • Diagnóstico de conectividad: route tables, SG egress, firewall listener Oracle
  • Parametrización de URLs JDBC del dominio vía variables de entorno (entrypoint)
  • Certificación de acceso a módulos Forms, generación de reportes y consola WebLogic
3

Ventajas y beneficios de la nueva arquitectura

La migración del aplicativo RECTOR hacia contenedores en AWS ECS aporta beneficios estratégicos y operativos para Banesco Seguros:

Escalabilidad horizontal

Posibilidad de agregar instancias adicionales de WLS_FORMS o WLS_REPORTS según demanda de usuarios, sin redimensionar servidores monolíticos.

Alta disponibilidad

Fallo aislado por contenedor: la caída de Forms no afecta Reports ni la administración del dominio. ECS puede reemplazar tareas automáticamente.

Portabilidad y consistencia

La misma imagen Docker validada en Compose se despliega en AWS sin divergencias entre entornos. En la nube, AWS Service Discovery mantiene la comunicación por nombres (*.forms.local) en lugar de IPs fijas, alineada con el patrón definido en desarrollo.

Gestión centralizada

Un único dominio WebLogic compartido (EFS) permite administrar RECTOR de forma unificada con ejecución distribuida en Fargate.

Reducción de costos de infraestructura

Fargate elimina la gestión de servidores EC2 dedicados; pago por uso de CPU/memoria según tareas activas.

Despliegue ágil y CI/CD

Imágenes versionadas en ECR, task definitions versionadas y despliegue controlado por revisión sin downtime prolongado.

Aislamiento y seguridad

Cada componente en su propio contenedor con security groups, IAM roles y secrets gestionados. Comunicación interna vía DNS privado Cloud Map.

Continuidad del negocio RECTOR

Se preserva Oracle Forms & Reports 14.1.2 y el dominio existente, modernizando solo la capa de despliegue sin reescribir la aplicación.

Ambientes paralelos para desarrollo y pruebas

La misma arquitectura containerizada puede replicarse en entornos independientes —desarrollo, calidad o pilotos— con contenedores y volúmenes propios, de forma rápida y segura. Así se habilitan nuevos proyectos y pruebas controladas de RECTOR sin interferir con el ambiente operativo.
